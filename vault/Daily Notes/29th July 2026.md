# 29th July 2026

Asked for the next steps to make AlarmX hack proof and easy to use so it could launch this week. Said plainly that this week was never possible and why: Google requires a new developer account to run a closed test with twelve testers, continuously, for fourteen days before it can even apply for production access, and that clock cannot start until an APK exists. There is no APK, and there was no server either. Realistic date is late August, so everything got resequenced to reach an uploadable build as fast as possible rather than to pretend.

Then built the two things that could actually be finished and proved today. The backend became a running service instead of four modules nobody called, which finally made the security requirements testable at all — thirty-seven hostile requests now get fired at it. Sessions became opaque random tokens rather than JWT, which removes a whole family of failures instead of defending against them. Two real bugs fell out: the AdMob callback was rate limited with the per-user rule, and since Google's callbacks all come from a few addresses that would have throttled every user's earnings at once in production. The IDOR and replay tests were each checked against a deliberately reintroduced bug before being trusted, because a security test nobody has watched fail is decoration.

Also moved the onboarding, permission and per-manufacturer battery logic into pure Kotlin so it is genuinely tested rather than reviewed. The Redmi and Realme battery killers are the single biggest technical risk in the product and were previously nowhere in the code. And cut the panchang calendar from v1 while keeping the widget — four weeks of licence, almanac cross-checking and native-speaker review for a feature that earns nothing directly.

546 checks passing. The honest gaps are written down: no database here so the Postgres store has never actually run, nothing is deployed, and the ad callback confirms a view without carrying revenue.
